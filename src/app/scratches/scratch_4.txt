 Editor
===============
 - Der Editor muss wissen, ob von einer Resource eine Local-Variante vorhanden ist, und muss diese wiederherstellen
   können
    a) delete auf Server-Resource und keine Browser-Resource => lade lokal-Variante in den Editor
    b) delete auf Browser-Resource und keine Server-Resource => lade lokal-Variante in den Editor

 Ablauf:
   + Beim betreten des Editors wird das Model der aktuellen Resource(n) übernommen (Browser > Server > Local)
   + In einer Info wird dargestellt, worauf die Modelle im Spiel derzeit basieren.

   + Beim Editieren wird auf dem aktuellen Model gearbeitet und wenn Änderungen auf dem Modell stattgefunden haben
   wird eine Bestätigung nötig, ob die Änderungen wirklich discarded werden sollen.

   + Speichern ist unabhängig von Änderungen immer möglich, und geschieht grundsätzlich im Browser, wobei die
   Anzeige für die Basierung auf "Browser" umspringt. (=> RELOAD mit Resource-ID)

   + Über einen "Restore"-Button wird das aktuelle Modell auf das Ausgangsmodell hergestellt (= das was in der
   Herkunftsanzeige dargestellt wird) => RELOAD mit Resource-ID

   + Export as Code

   + Revert
      Öffnet Modal in dem für jede Resource die Quelle bestimmt werden kann:
       - code (falls vorhanden)
       - server-resource (falls vorhanden)

      Die Browser-Einträge werden hier auf jeden Fall gelöscht
      Server-Einträge nur, wenn vorhanden und das Ziel "code" ist




   Solange das aktuelle Modell keine Änderungen seit dem letzten Speichern hat, oder beim Initialen Model,
   wird keine Warnung beim Verlassen angezeigt, ebenso stehen in dem Fall folgende Optionen zur Verfügung:

    +  "Deploy to server" (falls Initial und source != "server" OR source = "browser"):
       - Das aktuelle Modell wird auf dem Server gespeichert und bei Erfolg, wird die Resource aus dem Browser
         gelöscht und das Herkunftsmodell angepasst => RELOAD mit Resource-ID

    + "Delete from Server" (falls Initial und source = "server" und local-Resourcen vorhanden)
       - Die Resource-ID wird vom Server gelöscht und bei Erfolg, der Editor mit Lokal-Modell neu gestartet
       => RELOAD mit Resource-ID

=============================
 Resource-Edit+Storage
=============================

 1. Editor wird initialisiert
      - für jede Pane im akuellem Screen wird ein Eintrag erstellt:
        {id: pane.id,  config: <resourceClass>, data: pane}
        => screenResources

 2. Aus den (editierbaren) Screen-Resources wird eine Auswahl generiert

 3. Beim Klick auf Edit zu einer Resource
      - wird geschaut, ob resource.data === null ist, und wenn ja dann
        wird vom Resource-Loader die resource.id geladen und damit ein
        new resource.config(content) unter resource.data gespeichert

 4. Ein Editor wird geöffnet, welcher die resource bekommt
      - aus der resource erstellt der Editor sein initiales Modell auf
        dem dann alle Änderungen passieren
      - Bei der Initialisierung werden auch die verwendeten resource-ids
        als storageIds festgehalten
      - neben den eigentlichen Modell gibt es noch ein Resource-Tree
        Modell, welches die Beziehung aller editierten Resourcen
        zueinander anzeigt (mit Info über die Source der Resource)

 5. Beim "SAVE"
      - Aus dem aktuellem Modell wird dynamisch eine
        resource.config.Config-Instanz erstellt und über setter
        aufgebaut. Die Images und Audio gehen hier als on-the-fly
        generierte Resources rein.

      - Es wird das resource.config damit instantiiert und dann über
        getResources() die gesplitteten Resourcen und deren Dependencies
        geholt

      - Es werden nun alle diese Resourcen und Dependencies im SM
        gespeichert und alle IDs aus dem storageIds, die nun nicht
        mehr vorhanden sind, werden per safe-delete aus dem screen
        gelöscht

      - wird die resource.data auf null gesetzt, damit beim nächsten
        Edit, das Modell auf den zuletzt abgespeicherten Resourcen
        erstellt wird

React-Guide

1: props VS state

- props können nicht innerhalb der Component selber geändert werden, sondern müssen immer von aussen kommen
- state wird in der Component gebildet:
    bei Klassen im constructor oder bei Functions über useState
- state kann sich nachträglich ändern über Aufrufe von setState (auch von aussen erreichbar) bzw. die setterMethod
- Änderungen von state-values sollte bei Arrays und Objekten immer neue erzeugen
- setStates() werden async ausgeführt, weshalb ein value nicht direkt auf einem anderen state-Value rechnen sollte
- ein Aufruf von setState triggert auch einen Aufruf von render(), aber das DOM dahinter ändert nur die Teile, die
  sich tatsächlich geändert haben (aber Achtung: alle SubComponents im Render rufen, ebenfalls render auf)
