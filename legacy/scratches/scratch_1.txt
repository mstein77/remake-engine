=====================================
 Resource-Dependencies
=====================================

A) simple (hidden) deps

  I.
  ------------------------------------------
  screen.x
    # json:fontMap

  --> const conf = new FontMap.Config(resource.json.fontMap);
      *1* conf.setImage(resource.image['myPic.png']);
      *2* conf.setImage(state.myPic);
      myFont = new FontMap(conf);

  An der Stelle hier muss die ImageResource entweder direkt im Screen.load oder im
  State.load geladen vorliegen.

  II.
  -------------------------------------------
   Der Benutzer speichert Änderungen an der JSON fontMap Resource...
   Der Editor bekommt das Image "myPic.png" und speichert in der JSON-Resource
   eine Referenz "image@image": "myPic.png"

   Das setImage() im Code überschreibt, diese Referenz mit der Image-Resource, die aktuell
   ja noch im load registriert ist.

   Wie reagiert die FontMap-Instantiierung auf das JSON das reinkommt?
    - da die Resource schon im Load aufgelöst wurde, müsste die ID nicht noch mal aus dem
      RL geholt werden (=> Flag für JSON-Resourcen)
    - Wenn das setImage() nachträglich entfernt wird, müsste die Referenz über den RL (oder
      besser: resource.image[ref]) aufgelöst werden
    - Damit die Image-Resource auch dann geladen ist, wenn die Image-Resource nicht explizit
      im Screen- oder State-Load registriert wird, müsste der Editor diese Dependency
      für den Screen festhalten... screen: ['fontMap' => 'myPic.png']

   Mögliche Instantiierungen:

   a) JSON-direct:  myFont = new FontMap({id: 'xy', image: RES})

        - alle mandatory keys (wie id und image) müssen hier vorhanden sein und RES muss eine
          gültige (bereits geladene) Image-Resource sein (Object, String?)
          Beim RL wird zuerst geschaut, ob zu der ID bereits eine JSON-Resource vorliegt.
          Das Configureable reicht dieses (oder das Constructor-) JSON an eine neue
          Config-Instanz durch und wird direkt resolved.

   b) Resource-direct: myFont = new FontMap(resource.json.myFontMap)

        - Das Configureable merkt, dass das JSON bereits resolved ist und reicht dieses
          dann direkt an eine neue Config-Instanz durch.

   c) JSON-indirect:
        conf = new FontMap.Config({id: 'xy'});
        conf.setImage(RES);
        myFont = new FontMap(conf);

        - Da die Config auf einem unresolved Json basiert, müsste zunächst geschaut werden
          ob der RL zu der ID eine Überschreibung hat, was dann zu einer neuen Instantiierung
          der Config mit dem Resource-JSON führen würde
        - Die hardcodierten Überschreibungen werden bei einer RL-Auflösung immer verloren
          gehen.

   d) Resource-indirect:
        conf = new FontMap.Config(resource.json.myFontMap);
        conf.setImage(RES);
        myFont = new FontMap(conf);

        - Die Config basiert hier auf einem resolved JSON, deswegen kann dies direkt in
          im Constructor resolved werden.
          Die nachträglichen Änderungen auf der conf sind im Editor sichtbar und können
          überschrieben werden, ABER diese werden nie im Spiel sichtbar sein, da hier
          hardcodiert im Code überschrieben wird. Ausnahme: es wird mit einer Resource
          selbst überschrieben, was aber sinnlos ist
