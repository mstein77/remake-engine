Resource ids:
====================
a) Image:

   Regexp:

   [a-z_-0-9]+(/[a-z_-0-9]+)*.(png|jpg|jpeg)

   Die Endung muss hier ein unterstütztes image-format sein.
   Durch / kann ein Subfolder auf dem Server angesteuert werden

   Beispiel:

       "mario-running.jpg"
       "sprites/plant_1.png"

b) Audio:

   Regexp:

   [a-z_-0-9]+(/[a-z_-0-9]+)*.(wav|mp3|ogg)

c) JSON:

   [a-z_-0-9]+(/[a-z_-0-9]+)*(.json)?

   Die Endung auf json ist hier optional

######################################
 Analyse: Editor Architecture
######################################

 1.) RasterCanvas MEMO (CssContext + CanvasRef)

     Redraw Canvas-BG + Raster falls Änderung an cellSize, border, width, height oder CssContext
     Setzt CanvasRef initial oder wenn sich das Canvas-Elem geändert hat

 2.) CellRaster (CssContext)

     Redraw der Cells mittels Renderer bei jeder Änderung an cells, render, cellSize, border oder
     CssContext

 3.) CellProviderRaster MEMO (eContext)

     ==> Registriert eine Update-Methode im eContext unter der editorId

     Generiert ein CellRaster bei Änderungen an posX, posY, width, height, zoom, renderOptions,
     wobei Änderungen innerhalb des CellProviders (Cell-Values, Dims) von Aussen über die update-
     Methode getriggert werden müssen!

 4.) FlexCellProviderRaster

     Berechnet die Width + Height für das CellProviderRaster anhand des verfügbaren Platzes,
     Registriert einen Resize-Observer auf dem Parent-Node, der eine Neuberechnung triggert.
     Redraw von Rulers und CellProviderRaster bei Änderungen an posX, posY, width, height, zoom,
     rulers, renderOptions oder CHILDREN

 5.) FlexCellProviderScrollRaster (CssContext)

     Erweitert ein Raster um H- und/oder V-Scrollbars falls die Breite/Höhe des Rasters nicht
     komplett dargestellt werden kann.

 6.) RasterOverlays (EditorContext)

     Erzeugt absolute positionierte Overlays für Cursor und Marker auf dem Raster und gibt über

     ==> eine Overlay-Ref, die von Aussen reingegeben wird eine Control-Klasse nach draussen. Auf

     dieser Klasse werden Basic-Modes und Actions registriert, die von Aussen noch um zusätzliche
     erweitert werden können.
     Enthält auch ein Mouse-Overlay und einen Window-Event-Manger

  -------------------------------
  A) BaseCellProviderIndexRaster
  -------------------------------

 7.) RasterViewGrid (eContext)

     Erweitert ein FlexCellProviderScrollRaster um ein Navigation/Resize/Shift-Controls-Grid und
     RasterOverlays, die um entsprechende Dim- und Shift-Operations erweitert werden

  -------------------------------
  B) BasicRasterView
  -------------------------------
     Erweitert ein RasterViewGrid um eine top und bottom-Toolbar über welche die Overlay-Actions und
     -modes getriggert werden können.

  -------------------------------
  C) BitmapEditor
  -------------------------------
     Erzeugt zu einem gegebenen Bitmap ein BasicRasterView um dieses zu editieren und ggf. zu
     speichern.

Oversize:

Verhalten von Marker-Bereich
 a) Rect
      markerX >= cellProvider.getWidth
        => reset
      markerY >= cellProvider.getHeight
        => reset
      markerX + markerWidth >= cellProvider.getWidth
        => markerWidth = cellProvider.getWidth - markerX
      markerY + markerHeight >= cellProvider.getHeight
        => markerHeight = cellProvider.getHeight - markerY

 b) Rows / Columns
      markerY >= cellProvider.getHeight
        => reset
      markerY + markerHeight >= cellProvider.getHeight
        => markerHeight = cellProvider.getHeight - markerY

 c) Row-/Column-Gap
      markerY > cellProvider.getHeight
        => reset

Verhalten von Selection:
 a) Rect:
      keine Änderungen aber Vorsicht bei Cursor-Matrix

 b) Rows/Columns:
      Kann alles bleiben, beim grow werden neue Zellen transparent

 c) Gap:
      Keine Änderungen

Delete auf SM ist möglich über
 - SM.deleteResources (->RL.clearBrowserResources)
 - SM.deleteJson|Image|Audio (nicht verwendet)
 - SM.deleteResource (Resource-Dependencies: ->deleteResource, ->deleteScreenResources)

a) saveDelete: löscht ein Resource nur, wenn keine Dependency (screen, indirect-target) mehr auf diese existiert
 - sollte von deleteScreenResource nach dem löschen aus <screen> auf sich selbst
   und alle Deps (d.h. dadurch abgestorbene dependencies) aufgerufen werden

b) delete Screen-Resource

   1. ermittel alle Screen-resourcen zu x => dels
   2. suche alle direct Einträge screen->id zu dels => directs
   3. lösche alle Resourcen zu dels
   4. sync dependencies
   5. return directs

   Wird im Editor ein Deploy ausgeführt, muss die Screen-Resource und ALLE ihre abhängigen Resourcen aus
   SM gelöscht werden

   Beispiel:
     SM hat <screen1>: json:font1
            <screen2>: json:textPane -> json:font1
            <screen3>: json:textPane2 -> json:font1

     User deployed <screen2>: json:textPane ...dadurch muss auch json:font1 aus SM deployed und gelöscht werden
     Wenn die Dependency <screen1>: json:font1 nicht im Code vorhanden ist, würde diesen verschwinden, es sei
     denn wir deployen die directen Abhängigkeiten mit
     -> <screen3>: json:textPane2 verliert zwar die Dependency, aber die ID steht weiterhin im json:textPane2
        und da diese über den Server aufgelöst ist, sollten wir hier keine Probleme haben

     !!! Aber was ist, wenn wir diese wiederum vom server reverten? !!!

 Constructor-Algorithm

     constructor(input) {
        let id = null;
        let confJson = null;
        let conf = input;

        if (typeof input === 'string') {
            id = input;
        } else if (input instanceof FontMap.Config) {
            if (!input.isResolved()) {
                id = input.id;
            }
        } else {
            confJson = input;
            if (!input.__resolved) {
                id = input.id;
            }
        }
        if (id !== null && RL.hasJsonResource(id) {
            confJson = RL.getJsonResource(id);
        }
        if (confJson !== null) {
            conf = new FontMap.Config(confJson);
        }
        if (!(conf instanceof FontMap.Config)) {
            throw Error('Invalid');
        }
     }

=====================================
 D e p e n d e n c i e s
=====================================

Der Resource-Loader, kennt die registrierten normalen und permanenten resource-ids.
Nach der Registrierung wird der load von einem Screen getriggert.

Vor dem Laden muss der RL
 - Für den aktuellen screen die direkten Resource-Ids ergänzen aus screen-deps.json
 - Für die resultierenden Resource-Ids die indirekten Resource-Ids ermitteln

Falls in der screen-deps noch eine nicht weiter verwendete Resource-Id steht, würde der RL mit einem
Fehler aussteigen, was schlecht wäre, diese ergänzten Resource-Ids müssten stattdessen als "optional"
markiert werden und nur zu einem Fehler führen, falls tatsächlich später auf diese zugegriffen wird

direct: {
    '':      ['r1', ...],     // hier stehen die dependent ids für state-build,
    'mario': ['r4', ...]
}

indirect: {
    'r1': ['r2', 'r3'],
    'r6': []
}

Verwaltung der direct-ids:

 a) Resource x wird gespeichert:
    -----------------------------
      source = x permanent ? '' : curr.screen;
      if (direct[source] === undefined) {
         direct[source] = [];
      }
      if (!direct[source].includes(x) {
        direct[source].push(x);
      }

      // overwrite indirect dependencies
      indirect[x] = deps;


 b) Resource x wird gelöscht
    ------------------------
      source = x permanent ? '' : curr.screen;
      if (direct[source] === undefined) {
        return
      }
      const pos = direct[source].indexOf(x);
      if (pos === -1) {
        return;
      }
      direct['source'].splice(pos, 1);

      // delete indirect dependencies
      delete indirect[x];


 c) Sync Screen-Resources for screen y
    ----------------------------------

      }
